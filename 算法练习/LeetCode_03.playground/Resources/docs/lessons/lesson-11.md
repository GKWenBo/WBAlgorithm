## 一、基础与生命周期

**Q：讲一次 BLE 连接的完整生命周期。**
外设在 37/38/39 广播 → 主机扫描发现 → 发起连接、外设停播 → 连接参数生效（连接间隔/从机延迟/监督超时）→ MTU 协商 → 服务发现建句柄表 → 读写订阅 → 断开或超时。（第 1 课）

**Q：GAP 和 GATT 的区别？**
GAP 管「连接怎么建立、谁是主谁是从」；GATT 管「连上之后数据怎么组织」（Service→Characteristic→Descriptor 三层树）。谁存数据谁是 GATT Server，与谁发起连接无关。（第 1/4 课）

**Q：为什么连接后必须服务发现，能不能缓存句柄？**
句柄是 ATT 属性表的行号，随固件升级重排，不能跨连接复用。系统层 GATT 缓存在设备 OTA 后会失效，导致读写莫名失败——安卓靠 `refresh()` 反射清缓存，iOS 靠外设发 Service Changed。（第 4 课）

## 二、数据面四象限（最能体现深度）

**Q：写有几种？通知有几种？怎么选？**
四象限：写方向 Write Request（有确认、可靠、慢）vs Write Command（无确认、快）；通知方向 Indicate（有确认）vs Notify（无确认）。判据一句话：**丢了能自愈用快的，不能自愈用可靠的**。指令用 Write Request，OTA 大数据用 Write Command，流数据（心率）用 Notify，关键事件（Service Changed）用 Indicate。（第 4/5 课）

**Q：Write without response 是不是像 UDP，会丢包？**
不是。BLE 链路层有 CRC + 重传，空中不易丢。真正的风险是**接收端应用层缓冲溢出**（发太快对方处理不过来），所以高吞吐写要自己做应用层流控。（第 4 课）

**Q：`setNotifyValue(true)` 底层做了什么？**
两步：本地向系统栈注册回调 + 向 CCCD（0x2902）写 `01 00`。安卓原生经典 bug 是只做第一步忘了写 CCCD，结果一个通知都收不到。iOS 一步搞定且不暴露 CCCD。（第 5 课）

## 三、私有协议（企业核心，必被追问）

**Q：链路层有 CRC 了，为什么还要应用层协议和 CRC？**
BLE 特征是字节管道不是消息通道，链路 CRC 只保每个空中包，管不到「一条业务消息」的边界。粘包（固件合并发）、半包（超 MTU 切分）都要应用层用「帧头+长度+CRC」自己重建边界。（第 6 课）

**Q：你的帧怎么设计的？**
帧头 `A5 5A`（位模式交替、抗误同步）+ cmd + seq（请求响应配对）+ len（2 字节小端，带上限防坏帧撑爆内存）+ payload + CRC16（覆盖 cmd..payload）。（第 6 课）

**Q：收到半包/粘包/坏帧怎么处理？**
一个组包状态机：缓冲区累积，找帧头→读长度→等整帧→校验 CRC→吐帧。坏帧不整段丢，只丢帧头两字节逐字节重同步，因为坏帧后半段可能藏着下一个真帧头。（第 6 课，13 条单测覆盖）

**Q：OTA 固件升级怎么设计？**
Write Command 冲吞吐传固件块 + 应用层流控（每 N 包等一个进度 Notify）+ 分块 CRC + 断点重传。传输走快通道，可靠性在协议层自己挣。iOS 别忘了 Service Changed，否则升级后句柄对不上。（第 4/6 课）

## 四、稳定性（区分资深）

**Q：断线了怎么办？**
先区分主动断开 vs 意外掉线，只对后者重连（用 `_userInitiated` 标志）。重连用指数退避 + 抖动（避免射频拥塞和惊群），封顶放弃交给用户。**重连成功后必须重新发现服务 + 重新订阅**——CCCD 随连接复位，漏了就是「连上了但收不到数据」。（第 7 课）

**Q：安卓 status 133 是什么，怎么治？**
GATT_ERROR，安卓的「万金油错误」，射频冲突/协议栈状态错乱/缓存不符都归它。第一条军规：connect 前 stopScan。再配指数退避重试、断开后延迟再连、必要时清 GATT 缓存。把它当概率问题（压低发生率 + 状态机保证可恢复），不是逻辑问题。（第 3/7 课）

## 五、双端差异（iOS ↔ Android）

**Q：iOS 和 Android 蓝牙最大的区别？**
① 设备标识：iOS 给随机 UUID 拿不到 MAC，Android 给真 MAC → 跨端绑定要用广播里的序列号而非地址；② CCCD：iOS 一步、不可见，Android 两步；③ MTU：iOS 系统定、Android 可请求；④ 后台：iOS 系统代管 + State Restoration，Android 要前台服务。（第 2/5/9 课）

**Q：后台怎么保持连接？**
iOS：`bluetooth-central` 后台模式（退后台不断连、事件唤醒 10s）+ State Restoration（被回收后设备事件拉活），但用户上滑杀 App 无解。Android：前台服务（常驻通知）+ 电池优化白名单引导（国产 ROM 会额外杀）。两端都靠自动重连兜底。（第 9 课）

## 六、进阶专题（问到算你赚）

**Q：配对（Pairing）和绑定（Bonding）的区别？**
配对是本次连接的加密协商；绑定是把配对生成的密钥**长期保存**，下次连接直接加密不用重配。涉及加密特征（如带锁的写）时系统自动触发。安卓 `createBond`，iOS 由系统在访问加密特征时自动弹窗，App 无法直接发起。

**Q：iBeacon 是什么？和普通广播的关系？**
iBeacon 是苹果定义的一种广播格式（放在厂商数据 0xFF 里：UUID + Major + Minor + 发射功率），只广播不连接，用于室内定位/触发。iOS 用 CoreLocation 而非 CoreBluetooth 处理它——这也是第 2 课「安卓扫描要定位权限」的根源。

**Q：BLE Mesh 了解吗？**
Mesh 是多对多组网（灯控、楼宇），基于 BLE 广播的 managed flooding 转发，和我们做的「一对一 GATT 连接」是两套模型。面试知道「Mesh ≠ 多个 GATT 连接，是广播泛洪组网」即可，深入是专门方向。

**Q：连接间隔怎么权衡？**
小间隔 = 低延迟高吞吐但费电；大间隔 = 省电但响应慢。iOS 对间隔有严格限制（会拒绝过小的请求）。产品按场景定：OTA/实时控制期临时调小，日常保连调大。（第 1 课）

**Q：BLE 通信安全吗？怎么防窃听和重放？**
默认**不安全**——不加密的空口用几百块的 nRF Sniffer 就能抓，指令还能被**重放**（录一段开锁帧原样重发）。两层防护：① **链路层**——走配对加密，BLE 4.2 起的 **LE Secure Connections** 用 ECDH（P-256）交换密钥，能抗被动窃听；但要抗中间人还得有认证手段（Passkey 输入、数字比较、OOB），**Just Works 模式不防中间人**，这是最常被追问的一点。旧的 LE Legacy Pairing 密钥交换有已知弱点（crackle 之类工具可破），新产品别用。② **应用层**——帧里带随机数/时间戳 + HMAC 签名，设备校验签名并拒绝重复 nonce，敏感操作（开锁、恢复出厂）额外做一次挑战应答。**CRC 只防误码不防攻击**，把这句说出来就赢了一半。（第 6 课）

**Q：什么是 RPA（可解析随机地址）？对 App 有什么影响？**
出于隐私，很多设备（含 iPhone 自身）广播的不是固定 MAC，而是**每隔十几分钟轮换一次的可解析随机地址**。只有绑定过、拿到对方 **IRK** 的主机才能把它解析回同一台设备。对 App 的直接影响：**安卓上「按 MAC 记住设备」也不再可靠**——重启扫描后同一台设备是个新地址。正解还是那句：把序列号放进广播厂商数据或 GATT 特征，用它做业务主键。（第 1/2 课）

**Q：BLE 传输速度大概多少？怎么提吞吐？**
实际有效吞吐通常在几十到几百 kbps（1M PHY 下常见 100–300 kbps，理想条件更高），远低于标称速率——因为每个连接事件的时隙、协议头开销、双端处理能力都要打折。提速四招，按收益排序：① **加大 MTU**（配合 4.2 的数据长度扩展 DLE，单包 251 字节，头开销占比大降）；② **减小连接间隔**并允许一个连接事件里发多包；③ **用 Write without Response / Notify** 这类无确认通道，别用一问一答；④ 双端都支持 BLE 5 时开 **2M PHY**（速率翻倍，代价是距离变短）。反过来，**省电**就是把这些反着调 + 用从机延迟。注意 ESP32（BLE 4.2）没有 2M PHY 和扩展广播，只能靠前三招。

**Q：要同时连很多设备（比如一个网关连十几台）怎么做？**
① **连接数有硬约束**——手机控制器通常稳定支撑 5–7 条，超了要排队轮转，别硬连；② **建连必须串行**，并发建连是 133 高发场景；③ 每台设备**独立状态机 + 独立退避**，退避一定带抖动（否则网关重启会惊群）；④ **射频时间是共享的**，连接数越多每条的吞吐越低，要把连接间隔调大、把大数据传输错峰；⑤ 设备多时优先用**广播上报**（厂商数据里带状态）代替长连接，只在需要下发指令时才连——这是真实网关产品的常见架构，能说出来很加分。

**Q：蓝牙问题怎么抓包分析？**
安卓：开发者选项打开「蓝牙 HCI 侦听日志」，导出 `btsnoop_hci.log` 用 **Wireshark** 看空口交互（谁先断的、连接参数协商成什么、ATT 请求有没有回复）。iOS：装 Apple 的 Bluetooth 调试描述文件，用 **PacketLogger**（Additional Tools for Xcode）抓。硬件级：Nordic **nRF Sniffer**（nRF52840 Dongle + Wireshark 插件）能抓到手机看不到的链路层细节。再加一条常用的**交叉验证**：用 nRF Connect 连同一台设备，能连就说明问题在 App 侧。（第 7 课）

## 七、场景设计题（越到高级岗越常见）

这类题没有标准答案，考的是**结构**。统一的答题框架：**先问清约束 → 分层给方案 → 主动说取舍和失败路径**。

**Q：让你从零设计一个手环 App 的通信层，怎么做？**
先反问三件事：设备的连接形态（长连接还是按需连）、数据量级（实时波形还是每天同步一次）、有没有 OTA 和安全要求。然后分层答：**传输层**——一条 Write + 一条 Notify 当双向字节管道；**协议层**——帧头 + cmd + seq + len + payload + CRC，请求响应按 seq 配对、带超时重发和幂等，大数据分包走 Write without Response + 应用层流控；**会话层**——连接后握手（协议版本协商 + 鉴权），MTU 协商完再开始传，重连后重做握手和订阅；**稳定层**——重连状态机（退避 + 抖动 + 上限）、断点续传、结构化日志；**架构层**——协议和解析做成纯函数下沉，BLE 能力走接口 + Mock 双实现，保证能测能离线演示。最后主动说取舍：「如果只是每天同步一次数据，就不做长连接和保活，按需连接省电得多。」

**Q：协议要升级，怎么保证新旧 App 和新旧固件都能互通？**
① 帧里预留**协议版本字段**，连接握手时协商取双方都支持的最低版本；② **只增不改**——新增 cmd 而不是改老 cmd 的语义，payload 用 TLV 结构让老端能跳过不认识的字段；③ 设备侧对**未知 cmd 回明确错误码**而不是静默丢弃，App 才能给出「请升级固件」的准确提示；④ 灰度：先发能兼容旧协议的 App，再推固件 OTA，最后才下线旧协议分支。**「App 能升级、固件在用户手上升不动」是这题的核心矛盾**，答的时候点出来。

**Q：用户说「我的设备总是掉线」，你怎么推进？**
先量化再动手：① 拿到**可复现条件**（哪台手机、什么 ROM、距离多远、多久掉一次、App 在前台还是后台）；② 看**结构化日志**里的断线原因码和时间线，区分「链路掉」「被系统杀」「App 自己断的」；③ 用 **nRF Connect 交叉验证**同一设备同一环境，隔离是 App 还是固件/环境问题；④ 必要时抓 HCI 日志看是谁先发的断开；⑤ 定位到层之后再谈修法——是连接参数不合 iOS 要求、是国产 ROM 后台杀进程、还是重连状态机漏了分支。**流程比结论重要**，面试官看的是你会不会用证据推进，而不是直接猜。
