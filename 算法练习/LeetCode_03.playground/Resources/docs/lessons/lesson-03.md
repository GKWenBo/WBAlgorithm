# 第 3 课：连接管理（1 课时）

> 目标：从「看得见」到「连得上」。理解连接状态机、超时与断线感知，搭出设备详情页骨架。

## 一、先上一堂企业选型课：License 参数

写 `device.connect()` 时编译器会拦住你：`license` 是必填参数。这不是技术设计，是**商业模式**——flutter_blue_plus 从 2.0 起由 BSD 改为源码可见的双轨授权：

- `License.nonprofit`：个人 / 教育 / 非营利免费（本教学项目用这个）
- `License.commercial`：**商用需购买付费授权**

企业启示：① 选型时 License 审查和技术评估同权重，公司法务会挡掉「先用了再说」；② 因此不少商业项目停在 1.x（BSD 协议的最后版本）或转投 `flutter_reactive_ble`（Apache-2.0）；③ 我们课程继续用 2.x——API 更好，且你学到的概念在任何 BLE 库间平移。面试被问「Flutter 蓝牙库怎么选」，这段就是满分答案的骨架。

## 二、连接 API 的三个反直觉点

### 1. `connectionState` 流只会发 `connected` / `disconnected`

枚举里的 connecting/disconnecting 在 FBP 2.x 已废弃不再发射。「连接中」的转圈状态**必须自己管**（我们用 `busy` 标志包住 connect/disconnect 动作）。这背后是个正确的架构观：**UI 状态（用户视角的忙闲）≠ 链路状态（协议栈视角的通断）**，混在一起是无数蓝牙 App 状态错乱的根源。

### 2. 断线感知靠流，不靠返回值

`connect()` 返回只代表「这次建连动作结束了」。之后外设关机、走出范围、被系统踢掉——没有任何 Future 会告诉你，**唯一的耳朵是 `connectionState` 流**。所以 Controller 在构造时就订阅它，而不是在 connect 之后。断线后 `device.disconnectReason` 能拿到平台错误码：安卓是 GATT status（8 = 连接超时被动断线，19 = 外设主动断开，22 = 本地终止），iOS 是 NSError code。企业 App 用它区分「用户自己关的设备」和「信号问题掉线」，决定要不要自动重连（第 7 课）。

### 3. 连接前要停止扫描

安卓上扫描与建连共享射频资源，边扫边连会显著提高臭名昭著的 **status 133（GATT_ERROR）** 概率——这是安卓 BLE 最著名的「万金油错误」，官方文档不承认，Stack Overflow 上千贴。本课先记住第一条军规：**connect 之前 stopScan**（我们做在扫描页点击回调里）。133 的完整治理（指数退避重试、清 GATT 缓存）放第 7 课。

另外两个默认行为要知道：`connect()` 默认 `timeout: 35s`（企业一般压到 8–15s，用户等不了 35 秒）；FBP 在安卓上连接成功后会自动请求 MTU 512（`mtu: 512` 默认参数），iOS 忽略此参数由系统协商——第 6 课分包时会回来看它。

2. 安卓 App：扫描 → 点击该设备 → 详情页点「连接」→ 观察状态翻转为已连接（此时 LightBlue 里能看到 central 连入）。

## 高频面试题

**Q：安卓的 status 133 是什么？怎么治？**（安卓 BLE 第一名的面试题）
133 = `GATT_ERROR`，是个**没有具体含义的兜底错误码**：射频冲突、协议栈状态错乱、GATT 缓存与实际不符、资源耗尽都归到它。所以正确的心态是**把它当概率问题治理，而不是当逻辑 bug 修**——目标是压低发生率 + 保证发生后能自动恢复。具体手段：① **connect 前先 stopScan**（扫描与建连争射频，这是最有效的一条）；② 连接操作**串行化**，不要同时对多台设备发起连接；③ 失败后**指数退避重试**，别失败就立刻重连（第 7 课）；④ 断开后要 `close()` 释放 GATT client——安卓每个进程的 GATT client 数量有限（约 32 个），只 `disconnect` 不 `close` 会泄漏，泄漏满了之后**每次连接都是 133**，日志里能看到 `Registering too many GATT clients`；⑤ 怀疑是 OTA/固件改版导致缓存不符时，反射调 `BluetoothGatt#refresh()` 清缓存（第 4 课）。

**Q：`autoConnect` 传 true 还是 false？**
`false` 是**直连**：立即发起，速度快（几百毫秒），但设备不在范围内就会超时失败——适合用户点了「连接」按钮这种前台交互场景，本课就用它。`true` 是把设备挂进系统的**白名单后台连接**：不超时、设备一出现就自动连上，但首次建连明显更慢——适合「后台守候一台已绑定设备」的场景。企业里常见的组合是：前台 `false` 快速连 + 失败后走自己的退避重试，而不是无脑依赖 `autoConnect`。

**Q：连接超时该设多久？**
flutter_blue_plus 默认 35 秒，**太长了**——用户点一下等 35 秒才知道失败是不可接受的。企业一般压到 8–15 秒，失败后交给重连状态机去退避重试，UI 上立刻给反馈。这题考的是「知道默认值 ≠ 接受默认值」。

**Q：「连接中」这个状态为什么要自己维护？**
因为 `connectionState` 流是**链路状态**（协议栈视角的通断），FBP 2.x 里只发 connected / disconnected；而「转圈中」是**UI 状态**（用户视角的忙闲），比如用户点了连接、请求已发出但还没有任何链路事件——这段时间链路状态仍是 disconnected，可 UI 必须显示忙。**把用户意图状态和链路状态混成一个变量，是蓝牙 App 状态错乱的头号根源**，本项目用 `busy` 标志和 `connectionState` 分开维护，同一思想在第 5/7 课还会出现两次（`_desiredNotify` vs `isNotifying`、`_userInitiated` vs `disconnectReason`）。

**Q：`connect()` 成功返回之后，还有什么会让连接死掉？你怎么发现？**
设备关机/没电、走出范围（监督超时）、被系统或别的 App 踢掉、手机蓝牙被关、外设主动断开。**没有任何 Future 会告诉你**——`connect()` 的返回只代表「这次建连动作结束了」，唯一的耳朵是 `connectionState` 流。所以订阅必须挂在构造函数里（早于任何 connect），否则会漏事件。断线后读 `disconnectReason` 拿平台原因码：安卓是 GATT status（8 = 超时被动断线、19 = 对端主动断开、22 = 本地终止、133 = 通用错误），iOS 是 NSError code。企业 App 用它区分「用户自己关了设备」和「信号问题掉线」，决定要不要自动重连。

**Q：一台手机能同时连几个 BLE 设备？**
没有协议层的硬上限，实际取决于手机蓝牙控制器的资源，安卓常见能稳定维持 5–7 条连接，iOS 类似量级但没有公开数值。工程上更重要的是三点：① **连接数越多，射频时间被瓜分，每条连接的有效吞吐和稳定性都下降**；② 建连要**串行**排队，并发建连是 133 的高发场景；③ 多设备场景要给每台设备独立的状态机和重连退避（还要带抖动，避免同时掉线后惊群重连，见第 7 课）。

**Q：为什么连接前要停止扫描？**
安卓上扫描和建连共享同一套射频资源，边扫边连会显著抬高 133 的概率；即使连上了，持续扫描也会抢占连接事件的时隙，让吞吐和延迟变差。iOS 侧系统调度较好但同样不推荐。所以军规是：**connect 之前 stopScan**，连上之后需要继续找别的设备再重新开扫。
