# 第 6 课：私有二进制协议 ★企业核心（1 课时）

> 前 5 课学的是「蓝牙怎么用」，从这课起是「企业怎么用蓝牙」。真实产品里 App 和设备之间跑的不是裸字节，而是一套厂商自定义的帧协议。本课我们自己设计并实现一套，全程 TDD。

## 一、为什么需要「应用层协议」——链路层不是有 CRC 吗？

会被问的第一个问题。BLE 链路层确实有 CRC 和重传，但它只保证**「每个空中包」**的完整，管不到**「你的一条业务消息」**。原因是 BLE 特征本质是一根**字节管道**，不是消息通道：

- **粘包**：外设固件缓冲区攒了两帧一起 `notify` 出来，到达时 App 看到的是一串连续字节，边界丢了。
- **半包**：一帧超过 MTU-3，被切成多个通知分次到达。
- **无边界**：GATT 只定义「这次收到 N 个字节」，从不告诉你「这是第几条消息、到哪结束」。

所以应用层必须自带**帧同步**：用固定帧头找起点、用长度字段定终点、用 CRC 校验判断边界猜得对不对。这套东西就是私有协议。

## 二、帧结构设计：每个字段都不可省

我们设计的帧（多字节字段一律小端）：

```
┌──────┬──────┬─────┬─────┬────────┬─────────┬────────┐
│ 0xA5 │ 0x5A │ cmd │ seq │ len(2) │ payload │ crc(2) │
└──────┴──────┴─────┴─────┴────────┴─────────┴────────┘
                └──────────  CRC 覆盖范围  ─────┘
```

| 字段 | 作用 | 省了会怎样 |
|---|---|---|
| 帧头 `A5 5A` | 在字节流里定位帧起点 | 粘包/垃圾字节后再也找不到帧边界 |
| `cmd` | 命令字，区分业务（读配置/写配置/OTA…） | 收到帧不知道是什么请求 |
| `seq` | 序号，请求响应配对 + 丢包检测 | 并发请求时对不上是哪条的回复 |
| `len` | 负载长度，定位帧尾 | 不知道 payload 多长，无法切分粘包 |
| `payload` | 业务数据 | — |
| `crc` | 覆盖 cmd..payload，校验完整性 | 无法判断帧边界是否猜对、有无误码 |

两个防御性设计（面试加分点）：

- **帧头选 `A5 5A`**：`0xA5` = `10100101`，`0x5A` = `01011010`，位模式交替、互为反码，在随机字节流里碰巧出现的概率低，抗误同步。
- **`len` 上限（512）**：损坏的 len 字段可能是 `0xFFFF`，若无条件等 65535 字节会让接收缓冲无限膨胀。超上限直接判坏帧丢弃——**永远不要相信长度字段**。

## 三、CRC-16/CCITT-FALSE

选它是因为它是嵌入式设备最常见的 CRC 变体（Modbus、蓝牙 SIG 很多规范都用），固件同事拿到「CRC-16/CCITT-FALSE, poly 0x1021, init 0xFFFF」这一句就能对上。实现见 [packet.dart](../../lib/core/protocol/packet.dart) 的 `crc16`——逐字节、逐位异或移位，纯整数运算。单测里用了业界标准校验值：字符串 `"123456789"` 的 CRC 必须等于 `0x29B1`，这是验证任何 CRC 实现对不对的「金标准」。

## 四、组包状态机：半包/粘包/坏帧的统一处理器

核心是 `PacketAssembler`（[packet.dart](../../lib/core/protocol/packet.dart)），它持有一个跨多次调用累积的缓冲区，每次 `feed` 新字节后循环尝试解帧：

1. **找帧头**，丢弃头之前的垃圾字节（处理垃圾前缀）；
2. 不足 6 字节（读不出 len）就**等下次**（处理半包）；
3. 读出 len，超上限→报错并跳过帧头两字节**重新同步**；
4. 整帧未到齐就等（处理半包）；
5. CRC 校验，错→报错并**从帧头之后逐字节重同步**（一个坏帧不拖垮整条流）；
6. 校验通过→吐出 `Packet`，缓冲区移除该帧，`while` 继续解下一帧（处理粘包）。

「坏帧后逐字节重同步」是这套设计的灵魂：坏帧的后半段里可能藏着下一个真帧头，所以不能整段丢，只丢当前帧头的两个字节，让 `_indexOfHeader` 从后面重新找。测试 `CRC 错帧被报错并重同步，后续好帧仍可解出` 守护这条。

## 五、分包：把大数据按 MTU 切开

`PacketCodec.chunks(frame, mtuPayload)` 把编码后的整帧按写负载上限切块。上限 = **ATT_MTU - 3**（3 是 ATT 头开销），代码里从 `device.mtuNow` 取。这就是第 3 课「连接后自动请求 MTU 512」和第 4 课 OTA 流控的收口：MTU 越大，单包能塞的越多，分包数越少、吞吐越高。

发送端流程（见 [protocol_session.dart](../../lib/features/protocol/protocol_session.dart) 的 `send`）：`Packet → encode → chunks → 逐块 write`。接收端 `PacketAssembler` 自动把这些块拼回完整帧——**分包在发送端、组包在接收端，两者独立**。

## 高频面试题

> 这一节是「企业蓝牙岗」最能拉开差距的部分——前面的题网上都背得到，这里考的是有没有真做过产品。

**Q：链路层已经有 CRC 和重传了，为什么还要自己做应用层协议？**
因为 BLE 特征是一根**字节管道，不是消息通道**。链路层的 CRC 只保证「每个空中包」自身完整，管不到「你的一条业务消息」的边界：① **粘包**——固件缓冲区攒了两帧一起 notify，到达时是一串连续字节，边界没了；② **半包**——一帧超过 MTU-3 被切成多次通知分批到；③ **无边界**——GATT 只告诉你「这次收到 N 个字节」，从不说「这是第几条消息、到哪结束」。所以应用层必须自带**帧同步**：帧头定起点、长度定终点、CRC 判断边界猜得对不对。

**Q：你的帧结构怎么设计的？每个字段为什么不能省？**
`A5 5A | cmd | seq | len(2, 小端) | payload | crc16(2)`，CRC 覆盖 cmd..payload。帧头定位起点（省了粘包后永远找不回边界）；cmd 区分业务；**seq 做请求响应配对和丢包检测**（省了并发请求时对不上是哪条的回复）；len 定位帧尾（省了没法切分粘包）；CRC 校验完整性兼「边界猜对了没有」。两个防御性细节是加分点：① 帧头选 `A5 5A` 是因为 `10100101`/`01011010` 位模式交替、互为反码，在随机字节流里碰巧出现的概率低，抗误同步；② **len 必须设上限**（本项目 512），因为损坏的长度字段可能是 `0xFFFF`，无条件等 65535 字节会让接收缓冲无限膨胀甚至 OOM——**永远不要相信长度字段**。

**Q：为什么用「长度定界」而不是「转义定界」？**
两条主流路线：长度定界（帧头+长度+CRC，本项目）vs 转义定界（像 SLIP/HDLC，用 `0x7E` 当边界符，数据里出现边界符就转义）。长度定界的优点是**解析 O(1) 定位帧尾、不改变数据体积**，适合 MTU 受限的 BLE；缺点是长度一坏就得重同步（所以要配上限和 CRC）。转义定界的优点是任何时候都能靠边界符重新对齐，缺点是**最坏情况数据膨胀一倍**、编解码要逐字节扫描。BLE 上包长本来就紧张，主流固件协议都选长度定界。

**Q：半包、粘包、坏帧怎么统一处理？**
一个**组包状态机**（`PacketAssembler`），持有跨多次回调累积的缓冲区，每次喂入新字节后循环尝试解帧：找帧头（丢弃前面的垃圾字节）→ 不足 6 字节读不出 len 就等下次（半包）→ 读出 len，超上限就报错并跳过帧头两字节重新同步 → 整帧没到齐继续等（半包）→ CRC 校验，错了从帧头之后**逐字节重同步** → 通过就吐出一帧、缓冲区移除、`while` 继续解下一帧（粘包）。关键设计是**坏帧不能整段丢**：坏帧的后半段里可能藏着下一个真帧头，整段丢会连累后面的好帧，所以只丢当前帧头的两个字节重新找。本项目 13 条单测把这些边界全覆盖了。

**Q：CRC 用哪个？怎么保证和固件同事对得上？**
用 **CRC-16/CCITT-FALSE（poly 0x1021, init 0xFFFF, 不反转, xorout 0x0000）**——嵌入式最常见的变体，把这一串参数发给固件同事就能对齐。跨语言一致性靠三件事：① **约定字节序**（我们全用小端，和 ARM/ESP32 原生一致，避免固件侧再转换）；② 用**业界标准校验值**自测——字符串 `"123456789"` 的 CRC 必须等于 `0x29B1`，这是验证任何 CRC 实现对不对的金标准；③ 双方共用一组**测试向量**（同样的输入字节 → 同样的整帧十六进制），各自跑单测，联调前就能发现不一致。

**Q：一帧超过 MTU 怎么办？分包在哪、组包在哪？**
按 **MTU-3** 把编码后的整帧切块逐块写出去（本项目 `PacketCodec.chunks`，上限从 `device.mtuNow` 取）。**分包在发送端、组包在接收端，两者独立**——接收端的状态机根本不关心对方是怎么切的，它只认帧头和长度。工程注意点：MTU 协商完成前要按 20 字节保守切；换设备/重连后 MTU 可能变，切包上限要重新取。

**Q：请求发出去没回应怎么办？重发会不会导致设备执行两次？**
两件事分开做：① **超时重发**——每条请求按 seq 挂一个待响应表 + 超时定时器，超时后重发，重发 N 次仍无响应就上抛失败（同时触发链路层面的健康检查）；② **幂等**——重发意味着设备可能收到两次，所以**命令必须带 seq，设备侧对相同 seq 只执行一次、直接回上次的结果**。写配置这类天然幂等的还好，「电机转 10 圈」这种累加型指令不做幂等就会出事故。断线重连后要把待响应表清空、seq 复位，避免旧响应串到新会话（第 7 课）。

**Q：私有协议要不要考虑安全？**
要，而且这是很多产品的真实漏洞。BLE 空口可被嗅探（一台 nRF Sniffer 几百块），如果不做配对加密，指令是明文、还能被**重放攻击**（录一段开锁指令重发）。分级做法：① 有条件就用蓝牙自身的 **LE Secure Connections 配对 + 绑定**，让链路层加密（ECDH 密钥交换，抗被动窃听）；② 应用层再加一层——帧里带**随机数/时间戳 + HMAC 签名**，设备校验签名并拒绝重复的 nonce，重放就失效了；③ 敏感操作（开锁、支付、恢复出厂）额外要求一次挑战应答。面试能主动提到「防重放」，比只会说「加个 CRC」高一个层次——**CRC 防的是误码，不是攻击**。
