# 第 10 课：综合项目「设备管家」全流程验收（1 课时）

> 不引入新知识，把前 9 课串成一条完整的产品级链路，做一次双端真机验收。App 现在有了正式首页 [home_page.dart](../../lib/features/home/home_page.dart)，三个入口：真机模式、离线演示、双端信息。这一课是给你一份能对着做、也能对着讲的验收脚本。

## 一、架构总览：一张图讲清全貌

```
                    ┌─────────────── UI 层 ───────────────┐
   HomePage ──▶ ScanPage ──▶ DevicePage ──▶ ProtocolConsole
   （门面）      （扫描）      （连接/GATT/订阅/重连）   （私有协议）
                    │            MockDemoPage（离线演示）
                    ▼
   ┌──────────── Controller 层（ChangeNotifier）────────────┐
   ScanController      DeviceController      ProtocolSession
   （扫描状态）     （连接/重连状态机/订阅）   （帧收发）
                    │
                    ▼
   ┌──────────── Core 层（纯逻辑，全单测覆盖）──────────────┐
   BleCentral 抽象接口 ── RealBleCentral / MockBleCentral
   protocol/packet     heart_rate     hex     backoff
```

三条设计主线，面试时能画出这张图 + 说清这三点，就是及格线以上：

1. **单向依赖**：UI → Controller → Core，永不反向。
2. **纯逻辑下沉**：协议、解析、退避全是纯函数，40 条单测不碰硬件。
3. **抽象隔离硬件**：`BleCentral` 接口把 FBP 关进防腐层，可 Mock 可测可换。

## 二、贯穿全程的三组「分层状态」

这是整个课程反复强调的思想，验收时重点自检：

| 意图/UI 状态（自己维护） | 链路/协议状态（来自底层） | 出自 |
|---|---|---|
| `busy`（动作进行中） | `connectionState`（通断） | 第 3 课 |
| `_desiredNotify`（想订阅什么） | `isNotifying`（CCCD 实况） | 第 5/7 课 |
| `_userInitiated`（是不是我要断的） | `disconnectReason`（为什么断） | 第 7 课 |

混用左右两列，就是蓝牙 App 状态错乱的总根源。

## 三、双端真机验收脚本（逐条打勾）

### A. 扫描与连接（第 2-3 课）
- [ ] 首页进「真机模式」→ 开扫描，Android 首次弹「附近的设备」权限
- [ ] 目标设备出现，RSSI 随距离变化；关掉外设 4 秒后条目自动消失（幽灵治理）
- [ ] 点进设备 → 连接成功，状态卡显示「已连接」；读取 RSSI 有值

### B. GATT 读写与订阅（第 4-5 课）
- [ ] 服务浏览器列出服务树，特征带属性徽标
- [ ] 对可读特征「读取」，HEX + 文本双显示
- [ ] 对可写特征「写入」`48 69`，对端看到值变
- [ ] 订阅心率（2A37）→ 顶部出现实时曲线，滚动刷新

### C. 私有协议（第 6 课）
- [ ] 进「私有协议控制台」→ 绑定写/通知特征
- [ ] 发送 cmd=10 payload=01 02 03 → 对端收到符合帧结构的字节
- [ ] 让对端回帧（含故意坏帧）→ 控制台解出好帧、坏帧报错并重同步

### D. 自动重连（第 7 课）
- [ ] 连接+订阅后关掉外设 → 状态变「断线，Xs 后第 N 次重连」，退避递增
- [ ] 1 分钟内重开外设 → 自动重连成功，**心率曲线自动续上**（订阅自动重建）
- [ ] 点「断开」→ 绝不自动重连

### E. 离线与双端（第 8-9 课）
- [ ] 首页「离线演示」→ 模拟器/真机零外设跑通心率曲线 + 协议回帧 + 故障注入
- [ ] 首页「双端差异」→ 正确识别当前平台，对照表可讲
- [ ] `flutter test` 全绿（40 条）

## 四、离线兜底：没带第二台手机也能验收

面试现场往往只有一台设备。用**离线演示**（首页第二个入口）可以零外设展示：扫描→连接→心率曲线→协议往返→故障注入下的重连与坏帧恢复，覆盖 B/C/D/E 的核心。加上 `flutter test` 的 40 条，足以证明全链路正确性。

## 高频面试题

> 这一课的题都是**围绕你自己的项目**问的，也就是面试里问得最久的那一段。答案要能落到具体文件和具体现象。

**Q：介绍一下你这个项目。**（30 秒电梯陈述，脱口而出）
「Flutter + flutter_blue_plus 做的 BLE 设备管家：完整实现了扫描、连接、GATT 读写、通知订阅，以及一套带 CRC 和半包粘包处理的**私有二进制协议**。稳定性上做了指数退避 + 抖动的**自动重连状态机**，重连后自动重建订阅。架构上把 BLE 能力抽象成接口做了真实和 Mock 双实现，所以协议层等核心逻辑有 40 条单测覆盖、能在没有硬件的 CI 上跑，也能离线演示。双端的设备标识、CCCD、MTU、后台保活差异我都处理过。」——**结尾主动递话头**：「其中私有协议和自动重连是我花时间最多的部分，可以展开讲。」

**Q：画一下你的架构，说说依赖关系。**
三层：**UI 层**（HomePage → ScanPage → DevicePage → ProtocolConsole，外加 MockDemoPage）→ **Controller 层**（ScanController / DeviceController / ProtocolSession，ChangeNotifier）→ **Core 层**（`BleCentral` 抽象接口 + Real/Mock 双实现，protocol、heart_rate、hex、backoff 纯逻辑）。三条主线：① **单向依赖**，UI → Controller → Core，永不反向，Controller 里不 import Widget；② **纯逻辑下沉**，协议、解析、退避全是纯函数，40 条单测不碰硬件；③ **抽象隔离硬件**，`BleCentral` 把三方库关进防腐层。

**Q：项目里哪几处体现了「意图状态 vs 链路状态」的分层？混用会怎样？**
三处：`busy`（动作进行中，自己维护）vs `connectionState`（通断，来自底层）——第 3 课；`_desiredNotify`（用户想订阅什么，不随断线清空）vs `isNotifying`（CCCD 实况）——第 5/7 课；`_userInitiated`（是不是我要断的）vs `disconnectReason`（为什么断）——第 7 课。混用的后果非常具体：拿链路状态当 UI 状态就没有「连接中」的转圈；拿链路状态当订阅意图，重连后订阅就再也回不来（「连上了但收不到数据」）；不记用户意图，用户点断开会被自动重连立刻拉回去、永远断不掉。**这一组分层是整个课程复用最多的思想，能一口气举出三例，说明是真做过而不是背的。**

**Q：如果要把 flutter_blue_plus 换掉，要改哪些文件？**
理想情况只改一个：`lib/core/ble/real_ble_central.dart`——它是唯一 import FBP 的文件，负责把三方类型转换成项目自己的中立模型（`BleScanHit` / `BleService` / `BleChar` / `BleConnState`）。换库就是照 `BleCentral` 接口再写一个实现。**诚实加一句**：本项目第 2–7 课的页面出于教学演进仍直接用 FBP，那部分要跟着改；生产项目的正解是所有页面都走 `BleCentral`，把三方库彻底关在防腐层里——这个「知道现状不完美、也知道正解是什么」的回答，比假装架构完美更能加分。

**Q：面试现场只有一台手机，怎么演示？**
走**离线演示**入口（首页第二项）：Mock 实现零外设跑通扫描 → 连接 → 心率曲线 → 协议帧往返 → 打开故障注入看坏帧重同步和自动重连，覆盖核心链路的绝大部分；再跑一遍 `flutter test` 的 40 条单测证明协议层正确性。**这本身就是「可测试架构」价值的现场证明**——顺势就能把话题引到第 8 课的分层设计上。另外随身带一段「掉线 → 自动重连 → 心率曲线自动续上」的录屏，30 秒说明问题。

**Q：这个项目里你遇到过最难的问题是什么？**（行为题，按「现象→定位→根因→修复→防回归」讲）
推荐讲**「重连成功但收不到数据」**这条线：现象是状态显示已连接、读写正常，就是没有通知，极具迷惑性；定位过程是先排除固件（用 nRF Connect 连同一设备能收到）、再看日志发现重连后没有任何 CCCD 写入；根因是 CCCD 随连接复位、订阅不跨连接；修复是把「订阅意图」持久化成 `_desiredNotify` 集合，每次重连后重建订阅；防回归是用 Mock 的故障注入按概率制造掉线，在测试里验证订阅确实被自动重建。**讲清「怎么定位」比讲清「怎么修」更重要**，前者才是面试官想看的能力。

**Q：如果让你继续做下去，下一步做什么？**（几乎每场都会问，一定要有准备）
按优先级说三件：① **把第 2–7 课的页面全部迁到 `BleCentral` 接口**，让防腐层真正闭合，同时补 Controller 层的测试；② **补 OTA 与安全**——分块传输 + 断点续传 + 签名校验，以及协议层的防重放（第 6 课提到但没落地）；③ **补后台保活的工程落地**——Android 前台服务的 Service 类、iOS State Restoration 的原生平台通道，目前只做了配置声明和原理讲解。能主动说出自己项目的边界在哪，比夸大完成度可信得多。
